# Firestore Security Rules: Parent Account Operations Notes

## Overview
This document specifies the exact read and write operations performed by the Hazri Tutor application on behalf of the tutor client without Cloud Functions (Spark plan architecture).

All operations are executed from the primary authenticated tutor session (except temporary user Auth creation which occurs strictly within an isolated secondary `FirebaseApp` instance and leaves no orphaned users).

---

## 1. Client Read Operations

### `users/{parentId}`
The tutor client observes and reads parent user profiles for students managed by the tutor to render the status and credentials state on the student detail screen:
* **Fields Read:**
  * `username` (string): Parent login identifier (e.g. `p-x7k9mq`).
  * `active` (bool): Whether parent access is currently enabled or disabled.
  * `mustChangePassword` (bool): Whether the parent account is awaiting initial password change upon first login.
  * `studentIds` (list of strings): Student IDs linked to this parent account.
  * `createdBy` (string): The UID of the tutor who provisioned the account.
  * `role` (string): Evaluated as `'parent'`.

---

## 2. Client Write Operations (Admin/Tutor Permissions)

### A. Create Parent Account (`users/{parentUid}`)
During student addition or initial parent account generation for an existing student:
* **Target Document:** `users/{parentUid}` (where `parentUid` is the UID generated by Firebase Auth).
* **Write Type:** `set` (inside an atomic `WriteBatch`).
* **Fields Written:**
  ```json
  {
    "role": "parent",
    "name": "<Parent Name or 'Parent of Student Name'>",
    "username": "<loginId>",
    "phone": "<student.parentPhone>",
    "studentIds": ["<studentId>"],
    "active": true,
    "mustChangePassword": true,
    "createdAt": "serverTimestamp",
    "createdBy": "<tutorUid>"
  }
  ```
* **Security Rules Constraint / Expectation:**
  * Caller must be authenticated (`request.auth != null`).
  * Caller must have `role == 'tutor'` and `active == true`.
  * The student (`students/{studentId}`) must belong to the caller (`resource.data.tutorId == request.auth.uid`).
  * The student must not have a pre-existing `parentId` (or if reissuing, see section B below).
  * `request.resource.data.createdBy == request.auth.uid`.

### B. Link Student to Parent (`students/{studentId}`)
Atomic update linking the student document to the new parent user:
* **Target Document:** `students/{studentId}`
* **Write Type:** `update` (part of the same atomic `WriteBatch` as above).
* **Fields Updated:**
  ```json
  {
    "parentId": "<parentUid>"
  }
  ```
* **Security Rules Constraint / Expectation:**
  * Caller must be the tutor assigned to this student:
    `resource.data.tutorId == request.auth.uid`

### C. Issue New Parent Login (Delete Old Account Document & Link New Account)
When the tutor re-issues credentials for a parent:
* **Write Type:** Atomic `WriteBatch` containing 3 actions:
  1. **Create new parent document:** `users/{newParentUid}` (same schema as section A).
  2. **Update student link:** `students/{studentId}.parentId = newParentUid`.
  3. **Delete previous parent document:** `delete users/{oldParentUid}`.
* **Security Rules Constraint / Expectation:**
  * The old parent doc must have been created by the calling tutor (`resource.data.createdBy == request.auth.uid`) or linked to a student belonging to the calling tutor.
  * Note: The old Firebase Auth user cannot be removed by the client SDK (requires Admin SDK) and is harmless because its Firestore user document is deleted and it is no longer linked to any student.

### D. Toggle Parent Active Status (`users/{parentUid}`)
When the tutor toggles enable/disable parent access:
* **Target Document:** `users/{parentUid}`
* **Write Type:** `update`
* **Fields Updated:**
  ```json
  {
    "active": true | false
  }
  ```
* **Security Rules Constraint / Expectation:**
  * Caller must be an active tutor.
  * Caller must be the creator of the parent account (`resource.data.createdBy == request.auth.uid`).

### E. Complete Student Deletion Cascade
When a tutor permanently deletes a student (`deleteStudentCompletely`):
* **Target Documents & Operations:**
  1. **Delete Attendance Records (`attendance/{attendanceId}`):**
     * Query: `attendance.where('studentId', '==', studentId).where('tutorId', '==', request.auth.uid)`.
     * Write Type: Batched `delete` operations in chunks of at most 400 documents until exhausted.
     * Security Constraint: `resource.data.tutorId == request.auth.uid`.
  2. **Update or Delete Parent Account (`users/{parentUid}`):**
     * If `users/{parentUid}.studentIds` contains only this student:
       * Write Type: `delete`
       * Security Constraint: `resource.data.createdBy == request.auth.uid && resource.data.role == 'parent'`.
     * If `users/{parentUid}.studentIds` contains other siblings:
       * Write Type: `update` with `FieldValue.arrayRemove([studentId])`.
       * Security Constraint: `resource.data.createdBy == request.auth.uid && resource.data.role == 'parent'`.
  3. **Delete Student Record (`students/{studentId}`):**
     * Write Type: `delete` (in the final atomic WriteBatch).
     * Security Constraint: `resource.data.tutorId == request.auth.uid`.

## 3. Credentials & Privacy Guarantee
* **PIN Handling:** The 6-digit random PIN is generated locally using `Random.secure()` and sent strictly to Firebase Auth over TLS via the secondary Firebase app.
* **Storage Policy:** The PIN is **never** written to Firestore, local databases (Hive/SharedPreferences), application state, logs, or error traces. It is displayed strictly once via the modal sheet and immediately discarded from memory on dismiss.
